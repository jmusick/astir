# AGENTS.md

Guidance for AI coding agents working in this repo. [README.md](README.md) owns what Astir is and how to set it up. This file owns how to work on it. Add gotchas here as you find them, and replace the "not built yet" notes as the code lands.

## What this is

Astir is a to-do app built around a daily list that resets every day. The web view and API run on a Cloudflare Worker with D1. The native apps are Tauri 2 and reuse the same React UI. The repo is **public**.

The v1 design lives in [docs/specs/2026-11-16-astir-v1.md](docs/specs/2026-11-16-astir-v1.md). Its **Decisions** table (D1, D2, …) is the source of truth for anything settled. Issues cite D numbers.
- Decisions marked `user` were made by the owner. Don't change them without asking.
- Decisions marked `agent` were reasonable defaults. Raise it if the code shows one is wrong.
- If you need to change a decision, update the spec in the same change and say so in the commit.

## Layout

One npm package at the root, no workspaces. The layout follows the Cloudflare Vite plugin's and Tauri's defaults so their docs apply as written.

- `src/`: the shared React UI. `App.tsx` picks between `AuthScreen.tsx` (signed out) and `today/TodayScreen.tsx` (signed in); `authMode.ts` reads the account form from the address, and `rememberedAccount.ts` lets Today open offline. `route.ts` keeps the open screen in the address hash (`#/` for Today, `#/lists/<id>`, `#/history/<day>`, `#/settings`). `TodayScreen` also renders `lists/ListsNav.tsx`, `lists/ListScreen.tsx`, the read-only `history/HistoryScreen.tsx` and `settings/SettingsScreen.tsx` (day boundary in `DaySettingsForm.tsx`, devices, export, sign-out and account deletion; `accountData.ts` has the export and last-active helpers); `today/ItemDetails.tsx` edits the notes, due date, reminder and subtasks D26 allows for each kind. Today renders one list (D47) through `ui/Sortable.tsx`, the drag-and-arrow-key reorder that lists and subtasks share; `today/AddForms.tsx` is the one add box, and `today/Buckets.tsx` the pick-row actions, the pool editor and `RecordPicks`, which saves picks once decided.
- `src/sync/`: the one TypeScript sync engine (D13). `engine.ts` is local-first and storage-agnostic; it talks to a `SyncStore` (`store.ts`; `indexedDbStore.ts` for the browser, one database per account, D45; a Tauri SQLite store implements the same interface later) and a `SyncTransport` (`transport.ts`, the HTTP API). `daily.ts` holds the pure Today model (one ordered list) and record builders, `lists.ts` the named lists, their due tasks for Today (D27) and subtasks, `buckets.ts` a bucket's pool, the day's picks and their record builders (D56–D62), `repeats.ts` the repeat and missed-setting rules read from schedule versions (D51, D52), `history.ts` past days recomputed from schedule versions and completions (D7, D40), and `records.ts` the lookups, semantic IDs and text limits both share. `exportData.ts` builds the JSON export (D29) from local records, history included. `reminders.ts` decides which reminders are due in a time window and builds the synced dismissal (D42). `day.ts` is the only place that decides what "today" is: `dayAt` turns an instant into the account day from the synced `day` versions.
- `src/reminders/`: reminders (D16, D36). `useReminders.ts` checks every 15 seconds for reminders due since the last check and syncs a dismissal when one is clicked or closed. In a browser it looks back at most two minutes and shows them with the Notification API; the Windows app looks back to its last check (kept per account), no further than the start of today (`catchUpFrom` in `src/sync/reminders.ts`), and shows native toasts through `src/platform/notifier.ts` and the `show_reminder` command in `src-tauri/src/lib.rs`; `permission.ts` shares the permission state, and `focusItem.ts` lets a clicked reminder open its row.
- `src/offline/`: the web view's service worker (D33). `shellCache.ts` holds its caching rules (network-first navigations that fall back to the cached shell, cache-first built files, never `/api`); `serviceWorker.ts` is the thin `/sw.js` entry; `registerServiceWorker.ts` registers it in production builds only.
- `tests/client/`: Vitest for `src/sync` with DOM types (`tsconfig.app.json`); `fake-indexeddb` stands in for the browser. `tests/sync-client.test.ts` runs the engine against the real Worker handler.
- `worker/`: the Cloudflare Worker. `index.ts` is a single-file dispatcher (as in Tagstash), `headers.ts` sets the API's security headers, `no-store` and the CORS allowlist.
- `worker/auth.ts`: web auth handlers and helpers adapted from Tagstash. Optional secret types live in `worker/env.d.ts`; generated bindings still come from Wrangler.
- `worker/sync.ts`: validates sync pushes and serves revision-cursor pulls. [docs/sync-api.md](docs/sync-api.md) owns the wire contract. `0002_sync.sql` stores all entities in `sync_records` (`0003_day_settings.sql` rebuilds it to add `day`), with per-entity views, reference/revision triggers and a final-state quota check.
- `public/_headers`: CSP, HSTS and friends for static assets only. Worker responses never get these.
- `migrations/`: D1 migrations for `astir-db`.
- `src/platform/`: the thin platform layer (D12). `platform.ts` detects the app (`isApp`) and picks the server origin; `api.ts` is every API request (cookie on the web, bearer device token in the app); `localStore.ts` picks IndexedDB or `sqliteStore.ts` (Tauri's SQL plugin); `appSignIn.ts` and `AppSignInScreen.tsx` are the app's browser sign-in. `nativeShell.ts` wraps the badge, tray events, start-at-login and the stay-awake lock; `useNativeShell.ts` wires them to the open account, `StartAtLogin.tsx` is the first-run offer and the Settings switch, and `quickAdd.ts` with `QuickAddBox.tsx` and `QuickAddSetting.tsx` is the hotkey box. `main.tsx` renders `QuickAddBox` instead of `App` in the `quick-add` window, and `UpdateBanner.tsx` above `App` in the main one. `updates.ts` checks, downloads and decides when to install (D38). `src/ConnectAppScreen.tsx` is the web page (`/connect-app`) that hands the sign-in to the app. Nothing here is Windows-specific.
- `src-tauri/`: the Tauri 2 app. `src/lib.rs` registers plugins (single-instance, autostart, deep-link, opener, SQL), builds the tray menu, keeps the window in the tray on close and starts hidden when launched with `--minimized`; tray actions that touch data are `astir://…` events for the UI; `capabilities/default.json` lists what the UI may call; `tauri.conf.json` sets the `astir://` scheme, the CSP and the NSIS bundle. `app-icon.svg` is Signal's stepped mark; regenerate `icons/` from it with `npx tauri icon src-tauri/app-icon.svg`.
- `tests/`: Vitest. Worker tests call the fetch handler directly with a stub env; no Worker runtime needed.
- `wrangler.jsonc`: the Worker, its D1 binding and the custom domain. `npm run cf:types` regenerates `worker-configuration.d.ts` (gitignored) from it, and `npm run typecheck` does that first.

## Gotchas

- **Appearance is a device preference.** `src/appearance/init.ts` runs from the HTML head and applies `astir-theme` before the app renders. `theme.ts` validates that preference, defaults to Signal or Midnight from the system preference, and follows storage events so the quick-add webview and other tabs stay in step. Palette tokens live in `themes.css`; keep the sign-in, update banner and quick-add box on those tokens too. Fonts are bundled locally for the CSP and offline shell.

- **`GET /api/health` must stay ahead of the `env.DB` check** in `worker/index.ts`, so it answers without D1. It reports the database as `ok`, `not configured` or `error` but always returns 200.
- **`/api` and `/api/*` run the Worker first** (`run_worker_first` in `wrangler.jsonc`). Without it, a browser navigating to an API path would get the React shell from the SPA fallback.
- **Adding a third-party script (Turnstile, analytics) means updating the CSP** in `public/_headers`. Vite's dev server doesn't apply `_headers`, so check CSP problems with `npm run preview`.
- **npm only installs versions at least 7 days old** (`.npmrc` `min-release-age`). `npm install pkg@latest` fails for a fresh release; pick an older one. A dependency with an install script must be reviewed into `allowScripts` in `package.json`.
- **TypeScript stays on 6.x** until typescript-eslint supports 7.
- **CI's high-severity audit runs through `npm run audit`.** The shared baseline stays at `critical` while `scripts/audit.mjs` permits only GHSA-fc5q-39xc-vjpf in transitive, dev-only picomatch 4.0.7 until Dec. 1, 2026 (no patched release as of Nov. 17). Every other high/critical advisory still blocks. Remove the exception and restore the baseline's default audit level when a patched version lands.
- **Email work uses Worker `waitUntil`**, keeping known and unknown addresses' responses alike. With no context (tests), it awaits inline. A failed send removes its token but keeps the account for a resend. Never log provider messages, addresses or tokens.
- **Auth writes need `X-Astir-Client: web` and a trusted `Origin`.** Browser JWTs are cookie-only and always checked against `browser_sessions` plus `users.token_version`. Logout revokes the row; reset bumps the version and revokes all browser sessions. Keep this check when adding protected routes.
- **Email-token redemption is a D1 transaction.** A conditional user update wins the claim, `changes()` gates token consumption, and a unique `claim_id` gates reset side effects. Don't chain `changes()` through optional rows or use a timestamp as the claim identity: concurrent requests can share a millisecond.
- **Auth tests use Node's built-in SQLite** to execute the real migration and transactional SQL. No extra SQLite package or Worker runtime is needed. Missing migrations fail auth closed; apply local migrations before testing the forms.
- **Turnstile's public test secrets omit the action field.** Only on HTTP loopback with a public dummy secret do we skip action validation. A real secret always checks the action; HTTPS always refuses dummy secrets and checks hostname as well.
- **Sync pushes are D1 transactions.** Keep the `json_each` upsert and final quota-check insert in one `DB.batch`. Only winning changes allocate a server revision. Pull cursors use those revisions, never client timestamps, and pushes never advance a pull cursor.
- **Client deletes go in the same push as everything else**, so quotas see the final state. The server ignores data on deletes, so a tombstone for an item it never saw is stored without data: the next pull hands `engine.ts` that tombstone, which marks its local copy `archive` and pushes the data back. If a push is rejected with 400 because completions or children reference such an item, the engine retries with the archive copies first and the tombstones after.
- **The service worker is built by the `astir-service-worker` plugin in `vite.config.ts`.** It emits `src/offline/serviceWorker.ts` as `/sw.js` and injects the build's file list (bundle plus `public/`, minus `_*` and dotfiles) and a version that names its cache. `sw.js` is a classic script, so the build fails if it shares a module with the app; keep `src/offline/shellCache.ts` out of the UI's imports. The dev server has no service worker, so test offline loading with `npm run preview`.
- **Offline start uses the remembered account.** `rememberedAccount.ts` keeps the signed-in account's id and email in `localStorage` so Today opens from IndexedDB when `/api/auth/me` can't be reached. Sign-out and a 401 from `me` clear it.
- **Deletes never cascade on the server, so the client sends them.** `removed(item, records)` tombstones a task's subtasks with it, and `removedList` its tasks and their subtasks, all keeping their data. A named-list task's reminder is a UTC instant entered in the account's time zone (`zonedInstant` / `wallTime` in `day.ts`); habit and today-only reminders are `HH:mm`.
- **A reorder edits only the moved records.** `reorder` in `records.ts` places the moved item between its neighbours (renumbering only when they're too close), so two devices reordering offline keep each drag. A habit's or today-only task's Today place is `todayPosition`; v1 records have none, and `todayPlace` sorts them habits first by shifting their creation-time `position` (D68), so no conversion is written. A due list task's Today place is `carryPosition` for the `carryDay` that equals its `dueDay`; until then it waits at the top. New daily tasks get `todayBottom` so they land last (D50).
- **Local edits are stamped by `SyncEngine.change`.** Record builders in `daily.ts` leave `editedAt` at 0; the engine stamps each edit strictly after the previous one for that record.
- **Day settings are versions, never edits of today.** Change them only through `changeDaySettings`, which picks the first day the new settings can govern without splitting the current one (D34). `TodayScreen` seeds the first version (`0001-01-01`, this device's zone, midnight) only after a full sync finds none. A today-only task's checkmark has no day on the wire, so `todayView` dates it from the completion's `editedAt` with `dayAt`.
- **A push to `main` deploys production.** The Worker is connected to Cloudflare Workers Builds (`npm run build` then `npx wrangler deploy`), so confirm with the user before pushing, and apply any new migration remotely first: builds never run migrations. The production Turnstile site key is the `VITE_TURNSTILE_SITE_KEY` build variable there, not a file in the repo.
- **Apply `0008_buckets.sql` remotely before deploying the buckets client.** It rebuilds `sync_records` to add the `pool` and `pick` entities; without it every push holding one fails.
- **A day's picks are computed, then recorded.** `dayPicks` works them out from picks done before that day (D61), keeps recorded ones in their slots unless skipped or paused/deleted while unchecked, and fills the rest from the line. `todayView` returns the fresh ones in `toRecord`, and `RecordPicks` saves them after the first sync. Pick IDs are `itemId:day:poolId`, so a slot two devices filled differently offline has two records; a checked one wins, then the latest. A bucket day's misses don't carry the task as a whole (`repeatCarry` skips them).
- **Apply `0007_daily_checklists.sql` remotely before deploying the checklist client.** Without it the server refuses a habit's subtasks. A repeating task's checklist is checked per occurrence: `subtaskDay` on a Today row is the day its carry began (or today), so a carried checklist keeps its checks (D55).
- **Apply `0006_repeating_tasks.sql` remotely before deploying the repeats client.** Without it the server refuses schedules and per-day completions on today-only tasks, so a push that makes a one-off repeat (or sets one to drop) fails and waits on that device.
- **Repeats and the missed setting are schedule versions.** Kinds are immutable, so a one-off made repeating stays a `today` item with versions, and a repeating task made one-off gets a version with no weekdays. `missed` is null on versions older clients write, and `missedOn` then keeps the previous version's. A one-off's own day is checked with `itemId:task` and its repeat days with `itemId:day`; `checkedOff` picks by the row's `completionDay`.
- **A carry is computed, never stored.** `repeatCarry` finds the earliest scheduled day after the last check whose missed setting rolls it over through today; one per-day check settles every occurrence up to it (D53). A carried row checks the day it's on (`itemId:day`, even on an unscheduled day), and History lists such a check under that day's tasks. The walk only runs for tasks that repeat and roll over, since Today looks at every one-off ever made.
- **Apply `0005_device_tokens.sql` remotely before deploying the app-sign-in server.** Without it, `/connect-app` and device-token requests fail; web sessions are unaffected.
- **Apply `0004_dismissals.sql` remotely before deploying the reminders client.** Without it, the server refuses `dismissal` records and the whole push fails, so every pending change on that device waits until the migration lands.
- **Changing a `sync_records` CHECK means rebuilding the table.** Drop every view and trigger that names it first, rename it, copy, then recreate them, as `0003_day_settings.sql` and `0004_dismissals.sql` do, so no view or trigger is left pointing at the old table.
- **A deleted account is told apart from a revoked one by its token.** `signedOutReason` in `worker/auth.ts` verifies the cookie's JWT (ignoring expiry) and, only if this server signed it and its user is gone, adds `reason: "account-deleted"` to the 401. The engine turns that into the `account-deleted` state and `TodayScreen` wipes the device; `App.tsx` does the same when `me` says so at startup. A plain 401 (revoked, expired) keeps local data and offers an export (D29, spec edge cases). Keep the reason on every protected route's 401, including the device-token routes #11 adds.
- **Native apps authenticate with a bearer device token, never a cookie.** Requests carry `X-Astir-Client: app` and `Authorization: Bearer <JWT>` (audience `astir-app`, a `device_tokens` row checked on every request, like `browser_sessions`). App requests skip the Origin check, and `APP_ROUTES` in `worker/auth.ts` limits which auth routes they reach; sign-up, passwords and deletion stay web-only. CORS lets the Tauri origins (`http(s)://tauri.localhost`, `tauri://localhost`) read responses but never with credentials, because every Tauri app shares those origins.
- **The app sign-in is PKCE over a one-time code.** `app_handoffs` stores the code's hash and the app's challenge; `/api/auth/app-token` claims it with one conditional `UPDATE … RETURNING` that also checks the verifier, so a wrong verifier doesn't burn the code, and a used or expired one never works. The app ignores `astir://` links unless it has a pending verifier, and uses that verifier once.
- **The SQLite store writes in one statement.** Tauri's SQL plugin runs calls on a connection pool, so `BEGIN`/`COMMIT` across calls isn't safe. `sqliteStore.ts` keeps records, pending flags and the cursor (`#cursor`) in one table and applies each write as a single `INSERT … SELECT FROM json_each … ON CONFLICT`. Keep it that way.
- **A hidden window must keep running.** WebView2 throttles a hidden page and may freeze it after about five minutes, and Tauri's `backgroundThrottling` setting doesn't work on Windows. `stayAwakeInTray` holds a never-released Web Lock, which keeps the page from being frozen; `useSyncEngine` syncs in the app whether or not the page is visible. Check sync, reminders and the rollover after the window has been in the tray for a while whenever this changes.
- **Only the main window touches data.** The quick-add box is a second webview with its own JS context, so it never opens the engine or SQLite; it `emitTo('main', …)` the title and the main window's `useNativeShell` saves it. The global shortcut is registered from the main window too, per device in `localStorage` (default `CommandOrControl+Alt+Space`). A failed `register` means another app holds the shortcut: the old one is put back and Settings says so.
- **Native reminders are Rust toasts with callbacks.** Tauri's notification plugin can't report clicks on Windows, so `show_reminder` uses `tauri-winrt-notification` and emits `astir://reminder-activated` or `astir://reminder-dismissed` (user-closed only) to the main window with the reminder's tag. A development build borrows PowerShell's toast app id; a release uses the app identifier, which only works once installed (#15's shortcut carries it). Clicking a toast after it has timed out into the Action Center does nothing. The command is allowed through `src-tauri/permissions/reminders.toml`.
- **Updates are signed, and the key must never be lost.** `plugins.updater.pubkey` in `tauri.conf.json` is the public half; the private key and password stay in `%USERPROFILE%\.tauri\` and the repo's `TAURI_SIGNING_PRIVATE_KEY*` secrets (README, "Releases"). Rotating the key strands every installed copy. The app's version comes from `package.json` through `tauri.conf.json` (`"version": "../package.json"`); `src-tauri/Cargo.toml`'s version isn't shipped. `.github/workflows/release.yml` fails a tag that doesn't match `package.json`.
- **Automatic updates install only when nobody is looking.** `shouldInstall` allows it within two minutes of launch or after ten minutes hidden in the tray; otherwise `UpdateBanner` offers "Restart to update". `UpdateSetting` also offers "Check for updates" in Settings: it joins any ongoing check/download and installs immediately at the user's request. The NSIS installer runs in `quiet` mode and is per-user (`installMode: currentUser`), so neither installing nor updating needs admin. Updates are skipped in development builds.
- **Windows has no numeric taskbar badge.** `setBadge` draws the count onto a 32-pixel PNG and sets it as the window's overlay icon (needs Tauri's `image-png` feature and `core:window:allow-set-overlay-icon`); other systems use `setBadgeCount`.
- **`src/sync` stays platform-free.** `tests/sync-client.test.ts` compiles under the Worker's tsconfig, so `transport.ts` takes the platform's `apiFetch` as an argument instead of importing it.
- **The export is built on the device, not the server.** It must work offline and after a revoke, so `exportNow` tries a short sync and then exports whatever this device holds, noting unsynced changes.
- **Sync tombstones are permanent and keep archive data.** A delete arriving before creation can receive its missing metadata later, while remaining deleted. Item kind, parent, list and original/creation day are immutable. Completions and schedules use semantic client IDs; see the API contract before building the client.

## Rules that shape the code

- **One codebase.** The browser and every native app share one React UI and one TypeScript sync engine (D12, D13). Rust in the Tauri app handles only native features: tray, notifications, hotkey, autostart, badge and updater. Data logic never goes in Rust, and the UI is never forked per platform.
- **No Windows-only assumptions outside the platform layer.** v1 ships web and Windows, but Mac, Linux, iOS and Android come next from the same code.
- **Local-first.** Every change saves to the local store (IndexedDB or SQLite) first and syncs later. Never make the UI wait on the network for a write.
- **Never lose a task.** Sync rules (D32, D39) mean:
  - The most recent edit wins per record, by the client's edit timestamp, clamped by the server.
  - A delete beats any edit, and deletes are tombstones.
  - Completions are their own records.
  - Rollover, sync and long offline gaps must never make an item vanish without a trace.
- **The day boundary comes from the account's time zone and day-start hour** (D6, D30), not the device's time zone. It's computed on the device, and there's no server cron.
- **History never rewrites itself.** Schedules are versioned with the day they take effect (D34, D40).

## Tagstash is the reference for the server side

The sibling repo [jmusick/tagstash](https://github.com/jmusick/tagstash) (locally `../tagstash`) is a live Stone Dragon Media product on the same stack. Copy and adapt its patterns for:
- auth: bcryptjs, jose, Turnstile, email verification and password reset through Cloudflare Email Sending
- in-code rate limiting and lockout
- security headers, CSP and the CORS allowlist
- account deletion

Read its AGENTS.md first: it records many non-obvious gotchas. Two differences to keep in mind:
- **Tagstash runs on Pages Functions. Astir runs on Workers with static assets.** Don't copy Pages-specific layout (`functions/`, `_headers`) as-is.
- **Don't import from Tagstash.** Copy and adapt. The two apps must be able to change independently.

Astir's `.github/workflows/release.yml` builds the Windows installer and hands it to the shared release workflow. CI and release workflows in other projects use the shared [jmusick/ci](https://github.com/jmusick/ci) workflows (locally `../ci`). Check there before writing a release pipeline from scratch.

## Secrets and keys

- The repo is public. No secrets, tokens, real `.dev.vars`, or account IDs that aren't already public.
- The Tauri updater's private signing key must never be committed. If it's lost, every installed copy is stranded. Keep it in CI secrets with a documented backup.

## Changelog and releases

- [CHANGELOG.md](CHANGELOG.md) follows Keep a Changelog. Its sections become the release notes on GitHub Releases and in the Windows app's update notice, so write entries for people who use Astir: what changed for them, not commit subjects.
- Add user-visible changes under `## [Unreleased]` as part of the change itself. Leave out refactors, CI, tests and chores.
- Releases are cut with the `/release` skill. It bumps the version from the Conventional Commits, turns `Unreleased` into the version's section, tags and pushes. Don't hand-edit version numbers outside that flow.
