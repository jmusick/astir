# Astir v1: a daily to-do list on the web and Windows

2026-11-16 · Draft · Written from an interview with the user

## Problem and why

Astir is a to-do app from Stone Dragon Media built around one idea: a **daily list that resets every day**. Habits you repeat (take vitamins, walk, read) clear their checkmarks each morning, and the one-off things you mean to do today sit beside them. Anything you didn't get to rolls into tomorrow, marked with how long it's been waiting. Alongside the daily list, you can keep your own named lists (Work, Groceries, Someday) that don't reset.

The main reason for building it is learning: how to build and ship a cross-platform app with Rust and Tauri, keeping as close to one codebase as possible. It starts with the web and Windows; Mac, Linux, iOS and Android follow later from the same code. A paid version might come someday, but not soon, so nothing in v1 is built for billing.

A good result: one React interface and one sync engine that run in the browser and in a Windows app, both working offline. Using it should feel rewarding enough that the user uses it every day.

## Goals

- A signed-in user sees today's list with a progress ring (done ÷ total) and can check items off in the web view and in the Windows app.
- At the user's chosen day-start hour, recurring items uncheck and unfinished today-only items move to the new day, carrying a "2nd day", "3rd day" tag. This happens on every device, offline too, with no server job.
- The Windows app and the web view both work fully offline and sync when a connection returns. A change made on one shows up on the other after both have synced.
- The web view does everything the Windows app does except reminders while closed and the Windows extras.
- From anywhere in Windows, a global hotkey opens a small box that adds a task to today.
- Anyone can sign up, verify their email, reset a forgotten password, export their data as JSON, and delete their account.
- The Windows app installs from GitHub Releases and updates itself.
- **Done for v1** (agent's proposal, accepted at summary): the user uses Astir every day for two weeks, across web and Windows, without falling back to another to-do app.

**Non-goals**

- Billing, paid plans, or anything built ahead for them.
- Sharing lists between users.
- Mac, Linux, iOS and Android builds. The code must not *prevent* them (no Windows-only assumptions outside the Windows extras), but none ship in v1.
- Recurrence beyond "every day" or "chosen weekdays" (no every-N-days, monthly, or "first Monday").
- Reminders in a closed browser (no Web Push).
- Code signing for the first releases.
- Microsoft Store distribution.
- A native Windows UI framework (WinUI and friends). Windows-specific learning comes through the tray, notifications, hotkeys, installers and updates.

**Anti-goals**

- Losing a task. A sync conflict, a rollover, a long offline stretch or a wrong device clock must never make an item vanish without a trace.
- Two codebases in disguise: separate UI code or separate data logic for web and Windows beyond a thin platform layer.
- A reset that feels like a chore. Rollover is automatic, with no morning triage screen.

## Users and scenarios

Anyone who signs up. The first and most important user is the builder, using it every day. Scenarios are ordered so each can be built and shown on its own.

### Plan and finish today on the web (priority 1)

The core loop: see today, add to it, check things off, watch the ring fill.

- **Given** a signed-in user with three recurring items scheduled for Monday and two today-only tasks, **when** they open Today on a Monday, **then** they see a "Habits" panel with the three recurring items, a "Today only" panel with the two tasks, and a ring at 0%.
- **Given** that view, **when** they check off one habit and one task, **then** the ring shows 40% and the header reads "2 done · 3 to go".
- **Given** a recurring item set to Mon/Wed/Fri, **when** it's Tuesday, **then** it doesn't appear in Today and doesn't count toward the ring.
- **Given** a brand-new account, **when** they open Today, **then** they see an empty state that invites them to add a first habit and a first task. It isn't an apology.

### The day resets (priority 1)

- **Given** a day-start hour of 4 AM in America/New_York, **when** the user checks an item at 1:30 AM on Nov 17, **then** it counts for Nov 16.
- **Given** a recurring item checked yesterday, **when** the day rolls over, **then** it appears unchecked today, and yesterday's completion is kept in history.
- **Given** a today-only task left unfinished yesterday, **when** the day rolls over, **then** it appears in today's "Today only" panel with a "2nd day" tag. After another unfinished day it reads "3rd day".
- **Given** the app open across the reset time, **when** the boundary passes, **then** the view rolls over without a reload.
- **Given** a device that has been offline for four days, **when** it opens, **then** it rolls over correctly: carried tasks show the right count and nothing is lost.

### Use the Windows app offline and stay in sync (priority 1)

- **Given** the Windows app with no network, **when** the user adds, edits, checks and deletes items, **then** everything works and the changes are kept locally.
- **Given** those offline changes, **when** the network returns, **then** they sync up, and changes made meanwhile on the web come down.
- **Given** the same task renamed offline on Windows at 10:00 and on the web at 10:05, **when** both sync, **then** both show the 10:05 name.
- **Given** the web view, **when** the connection drops after the app has loaded once, **then** it keeps working from IndexedDB and syncs later.

### Live in the tray (priority 2)

- **Given** the Windows app, **when** the user closes the window, **then** Astir stays in the system tray, keeps syncing, and still fires reminders.
- **Given** "Start with Windows" turned on, **when** the user logs into Windows, **then** Astir starts minimized to the tray.
- **Given** Astir running, **when** the user presses the quick-add hotkey from any app, **then** a small box appears. Typing a title and pressing Enter adds it to today's "Today only" panel and the box closes.
- **Given** four items left today, **when** the user looks at the taskbar, **then** Astir's icon shows a "4" badge, which updates as items are checked and clears at zero.
- **Given** a task with a reminder at 5:30 PM, **when** 5:30 PM arrives and Astir is running, **then** a Windows notification appears. Clicking it opens the task.

### Keep named lists (priority 2)

- **Given** a signed-in user, **when** they create lists named Work and Groceries, **then** both appear in navigation with counts of open items, and their tasks never reset.
- **Given** a task in Work with a due date of today, **when** they open Today, **then** it appears there too (see D27) and counts toward the ring.
- **Given** a task with subtasks, **when** they check all the subtasks, **then** the parent stays unchecked until they check it. Subtasks are a checklist, not an automatic completion rule.

### Look back at past days (priority 3)

- **Given** two weeks of use, **when** the user opens History, **then** they can pick any past day and see what was done that day: habits done out of habits scheduled, plus the tasks completed.

### Account life cycle (priority 1 for sign-up, priority 3 for the rest)

- **Given** a visitor, **when** they sign up, **then** they get a verification email through Cloudflare Email Sending and can sign in after verifying, following Tagstash's flow.
- **Given** a forgotten password, **when** they ask for a reset, **then** they get a reset link, rate-limited as in Tagstash.
- **Given** a signed-in user, **when** they open Settings, **then** they can set their time zone and day-start hour, see signed-in devices and revoke one, export everything as JSON, and delete the account.
- **Given** a device whose token was revoked, **when** it next syncs, **then** it signs out (see the edge cases for unsynced changes).

### Install and update on Windows (priority 2)

- **Given** a visitor, **when** they download the installer from GitHub Releases, **then** it installs. An unsigned build is expected to show a SmartScreen warning.
- **Given** an installed older version, **when** a new release is published, **then** the app downloads it in the background. It installs and restarts by itself once it has sat in the tray for a while or on the next launch, or sooner if the user clicks "Restart to update" (D38). No admin prompt appears.
- **Given** the Windows app, **when** it's first opened, **then** it offers "Sign in with your browser". The browser opens Astir's sign-in or sign-up page, and after signing in the browser hands control back to the app. The app is signed in and the data syncs down.
- **Given** the user signed in through the browser, **when** the `astir://` handoff link is opened by anything other than the waiting app (a stale link, or a second click), **then** it does nothing harmful. Each handoff works once and expires within minutes.

| D31 | **Generous per-account limits** in Tagstash's style, enforced by the Worker (lists, open items, note length, subtasks per task, sync request size). The exact numbers are open. | Prevents abuse with open sign-up. | agent |

| D33 | The **web view caches its app shell in a service worker**, so it loads and works offline after the first visit. | Without it, IndexedDB offline data can't be reached when the page itself won't load. | agent |

| D36 | **Missed reminders.** If Astir wasn't running at a reminder time, it shows the missed reminder once on next launch, as long as it's the same day. | Better than silently dropping a reminder. | agent |
| D37 | No billing or plan fields in v1. | Paid is "someday". It gets its own spec when it comes. | agent |
| D38 | **Updates are silent and install when idle.** The app checks at launch and every few hours and downloads in the background. | D39 | **Completions are separate records**, one per (recurring item, day) and one per task. Each has its own most-recent-edit-wins rule, apart from the item's own fields. | D40 | **Recurring schedules are versioned.** Each schedule change is stored with the day it takes effect, so "habits scheduled" for any past day can be recomputed and history never needs a snapshot written at the reset. | D41 | **Only today is planned.** Today-only tasks can't be added to future days. Future work goes in a named list with a due date (D27). | D42 | **Reminders.** A today-only task's reminder is a time on its day. A recurring item's reminder is a time on each scheduled day. A named-list task's reminder is a full date and time. | D43 | **Rate limiting is in the Worker's code**, using Tagstash's lockout and auth-event counters, so it doesn't depend on a Cloudflare dashboard rule or plan. A dashboard rule can be added on top later. | Works on any Cloudflare plan and is covered by tests. | agent |

## Approaches considered

**Technology for the native apps.**

| Approach | Trade-off | Outcome |
| --- | --- | --- |
| WinUI 3 with C#, plus a shared .NET core | Best for learning native Windows development and mature. Every later platform needs its own UI. | Recommended at first, then dropped once one codebase became the priority. |
| Rust with Windows Reactor (WinUI 3 in Rust, added to windows-rs in May 2026) | Native WinUI and Rust learning together, but very new, with reported build failures and few examples. | Rejected as too early. |
| Avalonia (C# and XAML) | One codebase for all five platforms, with skills that transfer to WinUI. The web view stays a separate React app. | Recommended as a balance; not chosen. |
| Flutter (Dart) | Most mature at reaching all five platforms. Dart is used only here, and there's little Windows learning. | Not chosen. |
| **Tauri 2 (Rust and React)** | One UI shared even with the web view, and Rust gets used. The UI work is web development rather than native Windows. | **Chosen.** |

.NET MAUI was left out because it has no Linux, and React Native because it has no real Linux support.

**Where sync lives.** A Rust sync engine would mean more Rust learning, but the web view would need its own data path, so the data layer would exist twice. **A shared TypeScript engine was chosen.** Rust stays for the native features: tray, notifications, hotkey, autostart, badge and updater.

## Constraints

- **Cloudflare:** Workers with static assets and D1. Tagstash's notes record that the free plan allows one rate-limit rule, so Astir's rate limiting lives in its own code (D43).
- **Tauri 2** on Windows 10 and 11. The auto-updater needs its own update-signing key pair (separate from Windows code signing), and its private key must be kept safe. Losing it strands installed users.
- **The repo is public**, under the non-commercial license (D21). No secrets in the repo.
- **Email** goes through Cloudflare Email Sending, as in Tagstash.
- **Mac, Linux and mobile later.** Keep platform-specific code behind a thin layer so the shared UI and sync engine don't assume Windows.
- **Builder's context:** one person, learning Rust and Tauri while building. Prefer well-documented paths over clever ones.
- **Existing code to copy from:** Tagstash, in the sibling folder `tagstash`, for auth, emails, rate limits, security headers, CSP, CORS and account deletion. Adapt it from Pages Functions to a Worker. Don't import it as a dependency.

## Edge cases and failures

- **Device clock is wrong.** Day boundaries use the device clock, which is unavoidable offline. When online, the app compares against the server's time and warns if they differ by more than a few minutes. Sync timestamps are clamped as in D32.
- **The time zone or day-start hour changes.** The change takes effect at the next reset (D34). A day is never split or doubled retroactively.
- **Travel across time zones.** The account's time zone decides. The app notices the difference and offers to update it (D30).
- **Offline across several resets.** The rollover catches up. Carried tasks show the correct day count, and habits for the missed days show as not done in history.
- **The same item is edited on two devices.** The most recent edit wins (D32). Edited on one and deleted on the other: the delete wins.
- **A recurring item is checked on two devices for the same day.** It's one completion, not two.
- **The server or D1 is down.** Clients keep working locally and retry sync with backoff. The UI shows a quiet "not synced" state, not an error wall.
- **A token is revoked or expired while there are unsynced local changes.** The app tells the user it was signed out, keeps the local data until they sign back in and sync, and offers a JSON export before clearing anything.
- **Account deleted on another device.** The next sync signs the device out and clears local data, after showing why.
- **A limit is reached.** The Worker rejects the change with a clear message ("You've reached 100 lists"). The client shows it and keeps the change local instead of discarding it, so the user can trim and retry.
- **Bad input.** Titles can't be empty. Notes and titles have length caps. Text is shown as text and never parsed as HTML.
- **A reminder time passes while the app is closed.** See D36. In the web view, a reminder whose time passed while no tab was open is not shown later.
- **The quick-add hotkey is taken by another app.** Settings says so and asks for another.
- **Empty states:** a new account (invite to add a habit and a task), a day with everything done (the ring is full and the message celebrates it, quietly), and an empty list.
- **An update fails or is interrupted.** The installed version keeps running, and the update is offered again on the next check.
- **Unsigned installer.** The download page or README explains the SmartScreen "More info → Run anyway" step until signing is in place.

## Open questions

- **Exact per-account limits** (lists, open items, note length, subtasks). The builder proposes numbers and the user approves them. This doesn't block anything, but it's needed before public sign-up.
- **When to pay for code signing** (for example, Azure Artifact Signing at about $10 a month). The user decides before promoting Astir publicly. It blocks only the public launch.
- **App icon and logo.** It could be made later with Codex image generation. It's needed for the installer, tray, taskbar and favicon. A placeholder is fine until then.

## Left to the builder

- Repo layout, package manager and monorepo tooling.
- The sync protocol's wire format (cursor or change-log details), within D13, D14 and D32.
- D1 schema and migrations, and the local SQLite and IndexedDB schemas, as long as they represent the same model.
- The routing library, if any, inside the Worker. Tagstash uses a single-file dispatcher.
- Exact colors, type, spacing and animation within the "bold progress" direction, and dark mode support.
- The default quick-add hotkey.
- Keyboard shortcuts in the main window.
- Ordering of items within panels and lists (manual drag-to-reorder or by creation), as long as the order syncs.
